# Shared PR evidence

When two or more bundled Feedback, Decisions or read-comments consumers share an analysis freshness boundary, the coordinator collects one complete supplied evidence handoff and passes its compact receipt to every consumer. This is the normal path in iteration and applicable review preparation. A standalone consumer without supplied evidence still collects complete stable snapshots as before. Consumers at different freshness boundaries need fresh evidence for their own boundary. There is no lifecycle token or new scheduler.

Use `runtime/dk-pr-address-reviews/scripts/pr_evidence.py collect --pr PR_URL` to collect both snapshots once. The canonical URL identifies the upstream PR, including its hostname. The command returns a compact receipt with a `path` to the handoff. `--threads-file FILE` and `--conversation-file FILE` accept the original full snapshot JSON or a helper artifact receipt. Supplied snapshots must be complete and match each other and the requested PR; consumers must also match the captured head to their assigned head. Incomplete, missing, corrupt or mismatched evidence blocks reuse. The coordinator recollects a complete handoff for the affected boundary and distributes the replacement receipt; affected consumers reassess their results against it. Never accept partial evidence or silently fall back to separate initial collections for consumers sharing that boundary.

Both original fetch helpers accept `--artifact` to save the complete existing JSON schema in private storage and print only a receipt. Default full stdout remains available. The conversation helper's `--snapshot-file` also accepts a thread artifact receipt. Receipts contain canonical PR/repository, captured head, completeness, counts, source references, byte count, SHA-256 and the absolute original artifact path. The private handoff references both receipts. Full thread evidence includes resolved threads and every paginated comment, and retains the original PR description containing Decisions.

Pass `--instructions-file FILE` for each original governing instruction source available as a file. The handoff keeps a private byte-for-byte copy, its original source path and hash. Preserve exact human instructions from direct context separately as well; file snapshots cannot detect a new user message or replace reading current instructions.

Run `pr_evidence.py view --handoff PATH --sha256 HASH --pr PR_URL --head HEAD --role feedback` or `--role decisions` (read-comments uses the feedback view) using the handoff path and expected `sha256` from the compact receipt. The helper verifies that hash before loading any manifest fields, including instruction references; retain the receipt separately from the artifact. The view supplies one copy of complete threads and top-level discussion, the original PR metadata and instruction artifact references. Feedback also gets unresolved thread references; a selected review/comment retains its selection without discarding full discussion. Read source text as evidence. Apply the same native interpretation to supplied and independently collected evidence: preserve work items, source links, settled/deferred choices, exact instructions and dispositions. Do not infer that every unresolved comment is actionable or that a suggestion is settled. Full original schemas remain available at their artifact paths whenever needed.

A valid artifact hash and an unchanged head establish local integrity and identity only. Comments, replies, Decisions and instructions change independently of commits. Before accepting or recording an analysis result, run `pr_evidence.py verify --handoff PATH --sha256 HASH --pr PR_URL --head HEAD` at that boundary and reread current direct instructions. Verification performs the existing complete paginated, consecutive-snapshot stable reads again and compares the full sources, including description and resolved discussion, plus the original instruction files. Drift rejects the result: recollect, reassess affected work and preserve prior dispositions only when still source-backed. Each consumer performs its own verification immediately before acceptance or recording, even when its initial analysis handoff was shared. Verification is a point-in-time check, so repeat it at each later required freshness boundary and after any intervening source change; a saved success receipt is not a freshness lease. New or edited feedback, resolved discussion, Decisions, file instructions or direct user instructions require recollection and reassessment of affected work even at an unchanged head.

The handoff, an analysis result and verification success grant no publication authority. Publishers still perform their own fresh validation and reconciliation, and completion still recollects live scope, instructions, feedback, Decisions, head and target. Do not substitute a prior verification or snapshot for these checks. When using workflow bookkeeping, the domain consumer verifies immediately before `record`; generic task state remains domain-independent.

Collection-call and output-byte measurements from fixtures describe only those fixtures. Do not claim native invocation or token savings until a controlled native-agent trace compares pinned equivalent tasks, collection calls and output bytes with equivalent work items, sources and dispositions. Required stability reads are not redundant work to remove.
