# Repository instruction sources

Repository files are discovered as evidence before they become dk-workflows rules. Resolve PLUGIN_ROOT from this skill installation's plugin root. Before loading repository guidance for a skill, run `python3 PLUGIN_ROOT/scripts/instruction_sources.py --checkout REPO --repository HOST/OWNER/REPO show`. Use the same repository identity as the workflow and configuration request, including when reviewing a fork; pass it on subsequent source reads too. Without an explicit identity the helper uses the checkout's origin. This read returns the saved choice, whether initialization is complete, discovered sources with their paths, kinds and selection status, and host limitations. It creates no configuration or request history. Existing private settings and direct user instructions remain separate governing inputs.

## Initialize and choose

When no choice is saved, initialize through `dk-workflows:dk-config` before continuing repository-source loading. Inside that skill or its configuration agent, perform initialization directly; do not invoke it recursively. Do not infer consent from the presence of `AGENTS.md`, `CLAUDE.md`, `.github/copilot-instructions.md` or another automation instruction file. Existing users without a saved choice also need this choice on their next native workflow invocation; preserving their old cache records does not adopt those files.

Use `read --source REPO_RELATIVE_PATH --discovery` to inspect candidate files as evidence. Present the relevant rules with their original paths and explain which are intended for automation and which for human contributors. Ask whether to follow automation and human guidance (`all`), human-facing guidance (`human`), or explicitly selected sources (`custom`), including any sources to exclude. Human-facing candidates include contributor, development and hacking guidance; classification is a discovery aid and does not establish authority. Inspect the relevant source text before explaining it. Offer exact source selection when a file mixes wanted and unwanted rules; a file-level choice cannot selectively adopt individual paragraphs.

Keep discovery text out of governing summaries and downstream instructions until the user settles the choice. Await that answer; a timeout, an unrelated settings request or a workflow command is not a source-selection answer. A user who already explicitly named the desired mode and sources has supplied the choice. Once settled, use the existing configuration request and its dedicated native agent to save one repository-scoped `instruction-sources` operation. The main agent relays necessary questions and records the user's answer under that request as needed. No additional approval is needed for the settled change.

A value has `mode`, `include` and `exclude` fields, for example:

```json
{"mode":"human","include":["docs/contributor-guide.md"],"exclude":[".github/CONTRIBUTING.md"]}
```

`human` selects discovered human-facing sources, `all` selects all discovered sources, and `custom` selects only exact included paths. Explicit includes add files; excludes override mode-based selection. The include and exclude lists must be disjoint. Paths are repository-relative references, not shell commands or globs. New discovered sources follow the saved mode and exclusions; a custom selection does not adopt newly discovered files automatically. The choice is specific to the current repository, without user or upstream inheritance. Read the current inventory when resuming; do not ask the same initialization question again while a valid saved choice exists.

Exclusions also apply to resolved aliases of the same source. Unsafe instruction symlinks remain unselected inventory entries so governing handoffs cannot reintroduce them; ordinary and discovery reads reject those links. An unsafe alias does not exclude its independently selected regular target unless the policy explicitly excludes that source or an alias. Handoff validation covers resources, instructions and inputs, including directory references containing excluded sources.

Git-ignored automation and contributor guidance participates in discovery and the saved selection too. Ignoring a local instruction file in Git does not adopt it or exempt its direct, alias or directory handoffs from source checks. Selected ignored files use the same content freshness checks as tracked guidance.

## Read, change and reset

After initialization, load selected files with `read --source REPO_RELATIVE_PATH`; ordinary reads reject unselected sources. Discovery reads remain available to explain a proposed change, with the same evidence-only boundary. Apply each file only within its documented scope. A saved source choice does not change the host's instruction priority, grant permission, or make every sentence in a selected source a repository-wide rule.

Inspect the current choice with `scripts/config.py --repository HOST/OWNER/REPO --checkout REPO show --section instruction-sources` or the source helper's `show`. Change it through `dk-config` using a repository-scoped `instruction-sources` set operation. Reset it using that domain's reset operation; reset replaces the choice with a minimal pending marker and requires initialization before the next repository-source load. The marker blocks managed task work until reinitialization, preventing fallback to legacy cached guidance. Neither action edits upstream repository files, resets budgets or clears original analysis.

Pass selected original source references and the current choice to downstream skills, including external reviewer skills. A receiver checks current selection before consuming repository guidance. Do not reintroduce excluded files through a saved summary, copied instruction artifact, preference-admission context, original reviewer result or an old handoff. Preserve historical evidence as evidence; recapture governing inputs and refresh affected analysis when its source choice or selected content changes. Source exclusions do not erase independently supplied user instructions or independently admitted private settings. If a copied artifact cannot be traced to its governing sources, treat its applicability as uncertain and refresh the affected handoff rather than promoting it to current rules.

Task definitions bind the repository checkout and a digest of the selected choice and source contents. Task capture validates that binding before reuse or acceptance; a changed binding requires rebuilding the affected assignment and handoff, rather than merely replacing its fingerprint while retaining an opaque old summary. Keep cache keys, original results and unaffected siblings; invalidation requires affected work to be refreshed, not a blanket cache reset. Before using legacy cached guidance after initialization, recapture it under the current source policy. Missing or invalid policy/source evidence blocks applicable reuse. Uninitialized low-level capture retains compatibility with existing fingerprints; the native initialization boundary above still applies.

## Host limitations

The host may have loaded repository or ancestor instruction files before a skill runs. dk-workflows cannot unload that context, override system/developer instructions or other higher-priority host rules, or prove that excluded text was never seen. Apply this source boundary before optional workflow reads and delegation wherever possible, and disclose any already loaded conflicting guidance. Explain the specific limitation to the user; do not claim that choosing human guidance disabled a host-enforced automation rule. Where the host cannot honor the requested exclusion, report the affected behavior as blocked or incomplete and explain that host-side instruction configuration must be changed by the user. Do not launch another Codex or Claude Code session as a workaround.

The helper inventories sources inside the checkout. Host-level and ancestor instructions remain subject to the host's own loading and precedence rules; disclose them when present rather than implying that an in-checkout inventory is complete host coverage. Configuration admission retains its ancestor `AGENTS.md` freshness checks independently of the optional in-checkout selection, so changes require fresh admission. Saved selection controls optional dk-workflows source adoption, not host security or instruction precedence.
