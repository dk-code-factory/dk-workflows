# Review another person's PR

Find issues, verify them and post a review. This workflow does not authorize code fixes, commit rewrites, scope splits, description or Decisions edits, feedback resolution or branch pushes. Use `dk-pr-fix` only when explicitly asked to maintain the PR. Direct invocation permits posting verified findings under effective policy. Analysis-only instructions disable publication. Approval and merging each need explicit user permission or their own enabled `dk-config` policy. Permission to post findings grants neither.

Follow [preference retrieval and handoffs](../docs/preferences.md#workflow-handoffs-and-reuse) in `review` mode for discovery and independent finding verification. Select records against each task's paths, evaluate conditions, and pass full records with applicable paths and decisions. Capture that handoff in managed inputs. Refresh before claims, recording and final coverage checks when paths, relevant preferences or consumed condition context change, including before expanding scope. Reuse unchanged conditional decisions and refresh only affected work through task state.

1. **Inspect and pin.** Resolve ownership through [PR routing](pr.md), selected roles and reviewers through [configuration](../docs/configuration.md), and complete discussion through [shared evidence](../docs/pr/supplied-evidence.md). Save original instructions, settled and deferred scope, existing feedback, Decisions with sources, target, base, head and effective action policy. Direct invocation may review your PR, but never approve the authenticated account's own PR. Save the run and permissions in operational progress. Narrower new instructions revoke affected pending actions.
2. **Find issues.** Follow [cycle hooks](../docs/cycle-hooks.md): when discovery or verification needs a new pass, check the remaining budget, save the cycle id and complete ordered `before_cycle` hooks before capturing final discovery inputs. Refresh inspection after hook effects. Hook tasks use the same run without reviewer budget flags. Invoke the configured coordinator, normally `dk-pr-reviewers-run`, under [the reviewer recipe](pr-reviewers.md). Pin complete inputs and save reports and native handles. Manage claims and reuse through [task state](../docs/task-state.md). Use the saved `--run RUN_ID --cycle CYCLE_ID` for discovery and verification claims in this pass. Changed source inputs require a new cycle; unchanged reuse uses none. Keep candidate findings separate from confirmed issues. Missing or incomplete required reports block a clean verdict. Preserve completed tasks. Follow [native handoffs](../docs/native-review.md).
3. **Verify independently.** Give a fresh native agent the candidate findings, original evidence, pinned source, governing scope and complete discussion. Assign verification only, without fixes or publication. Require it to challenge each claimed failure, inspect surrounding behavior and tests, reproduce when useful, check settled or intentional behavior, and check for prior fixes or reports. Return `confirmed`, `rejected` or `uncertain` for each finding, with source or reproduction evidence and severity. Confirmed findings also need a changed-line location. Preserve disagreements. No candidates means no verification invocation, but required discovery coverage must still be complete.

   Define a managed task with identity `dk-workflows:dk-pr-review` and responsibility `finding-verification`. Capture this skill, recipe, all governing references, original candidate outputs and exact pinned inputs. Assign verification only; do not invoke the full workflow recursively. Use the reviewers' claim, native outcome and recording contract. Failed or incomplete verification leaves candidates unverified. Save and recover it explicitly. Record the failed or incomplete attempt before its one eligible retry in the same cycle. Reserve `--retry` immediately before retrying, never on initial invocation. Uncertain findings block approval and merging, even if confirmed findings can be posted.

   After successful discovery, verification and finding dispositions, complete ordered `after_cycle` hooks before publication. Resume unfinished hooks in the same occurrence; reuse-only checks and same-cycle retries do not repeat completed hooks. Hook failures block the next boundary. Refresh affected evidence after hook changes; changed review inputs require another pass within the retained budget. Hooks inherit this workflow's permissions, including its prohibition on fixes and branch pushes.
4. **Prepare and post.** Remove duplicate verified findings already covered by current discussion or your reviews, including prior runs. Post only confirmed actionable issues with evidence and changed-line locations. Use `REQUEST_CHANGES` for blocking findings and `COMMENT` for nonblocking findings. Partial reviews use `COMMENT` and state remaining coverage or verification blockers. Never report partial or uncertain coverage as clean. Before publication, refresh head, target, scope and discussion, then recapture affected tasks. Changes require reassessment and fresh verification. Cached findings do not authorize actions. Use the configured publisher, normally `dk-pr-review-post`. Save exact payloads and operation receipts. Reconcile uncertain writes read-only before retrying.
5. **Approve when authorized.** Require all selected reviewers and needed verification to be complete, no unresolved blocking or uncertain findings, and current CI for the exact head through `dk-ci`. Recheck feedback, rules and coverage. Post `APPROVE` only when authorized and the authenticated actor differs from the author. If approval is disabled, return the review or post confirmed findings. Do not post an empty review just to mark progress.
6. **Merge when authorized.** Require complete clean review and verification, current CI, satisfied repository review requirements, and an open, non-draft, mergeable PR at the reviewed head and target. Refresh live inputs and task status immediately before dispatch. Use `dk-pr-publish` with `kind:merge-pr`, reviewed `head`, reviewed target `base` and authorized `merge_method` (`squash` or `merge`). The publisher checks current readiness and binds the request to the reviewed head. It does not bypass protection rules. Save the operation. After an uncertain outcome, reconcile the exact merge commit and actor. Changed source or an ambiguous outcome blocks further writes. Do not retry a merge.
7. **Report and resume.** Return reviewer and verification completion, finding dispositions, publication links, approval and merge receipts or blockers, and saved state references. Reread current governing inputs and recapture specs before claiming completion. Report each requested action separately: posting may be complete while approval or merging is blocked. Resume the same claims, run, retry budgets, CI deadlines and publication operations. Unchanged reruns must not duplicate comments, approvals or merges. Allow five review and verification cycles for changed inputs, with one retry per task for the same inputs. Stop with saved evidence when the budget is exhausted.
