# Review another person's PR

Follow [simplification review](../docs/simplification.md). For each selected reviewer runner, pass the live owning workflow selector to plan/preflight and managed leaves; do not copy a composed list into invocation overrides. Re-select the live plan before completion. Verify maintainability recommendations for concrete benefit, behavior preservation and bounded scope without requiring a functional bug; fix workflows assess and implement justified recommendations through their existing stages. Preserve ordinary review coverage.

Before repository guidance reads, follow [repository instruction sources](../docs/instruction-sources.md). Follow all discovered instructions by default, or the saved explicit source override; do not require a source-choice question or onboarding; pass only selected source references as current rules, retaining excluded historical material as evidence. Refresh affected guidance and analysis when that choice changes.

Follow [private workflow reporting](../docs/private-reporting.md). Operational reports, blockers, diagnostics, handles and receipts go only to the invoking user or private caller, never into external text. Pass this governing contract downstream; publication permission does not authorize disclosure.

Read `dk-workflows:dk-pr-review` through [skill-owned configuration](../docs/skill-configuration.md). Its resolved `architecture`, `tasks`, `finalizers`, `limits` and `permissions` govern selected invocations; follow list order and explicit parallel groups. Use `skill-plan` and managed `prepare`/`finish` for these lists. The stages below supply applicability and acceptance rules, not hidden fallback invocations. Preserve evidence when selected work cannot satisfy a mandatory readiness requirement. Skip verification only when complete discovery has no candidates, recording that applicability decision; never claim an unperformed verification pass completed. Place custom work before or after discovery and verification directly in the task list; repeat the selected tasks when a new pass is needed within retained limits.

Find issues, verify them and post a review. This workflow does not authorize code fixes, commit rewrites, scope splits, description edits outside the restricted architecture Decisions permission, feedback resolution or branch pushes. Use `dk-workflows:dk-pr-fix` only when explicitly asked to maintain the PR. Direct invocation permits posting verified findings under effective policy. Analysis-only instructions disable publication. Approval and merging each need explicit user permission or their own enabled saved policy, read directly under [workflow configuration](../docs/configuration.md). Permission to post findings grants neither.

Follow [preference retrieval and handoffs](../docs/preferences.md#workflow-handoffs-and-reuse) in `review` mode for discovery and independent finding verification. Select records against each task's paths, evaluate conditions, and pass full records with applicable paths and decisions. Capture that handoff in managed inputs. Refresh before claims, recording and final coverage checks when paths, relevant preferences or consumed condition context change, including before expanding scope. Reuse unchanged conditional decisions and refresh only affected work through task state.

At entry, retain the existing run and distinguish ordinary recovery from a renewed explicit user request to review. An exhausted allowance can receive a bounded `continue-run` grant under [retained budgets](../docs/task-state.md#retained-budgets), with a stable user-request id and exact instruction/source. Replays retain that id. A new session alone grants no cycles or publication permissions.

When entered from the publisher's [standalone-to-merge bridge](../docs/pr/ci-approval.md#standalone-review-followed-by-a-merge-request), preserve the original direct merge request and its exact authorization through all handoffs. Resume compact managed status and reuse current original results under their existing definitions and native evidence contracts. Complete missing or stale selected work and obtain CI approval evidence through the ordinary stages below; an unbound standalone report is context, never fabricated managed coverage. After evidence and execution approval, observe CI and return to the original publisher merge continuation. Do not stop at handing off or require the user to repeat an already authorized merge. Explicit policy, missing native execution/evidence or permissions, changed inputs, failed CI and unresolved review findings remain real blockers with their exact recovery step.

1. **Inspect and pin.** Resolve ownership through [PR routing](pr.md), selected invocations and reviewers through [configuration](../docs/configuration.md), and complete discussion through [shared evidence](../docs/pr/supplied-evidence.md). Preflight eligible stages separately through `skill-preflight --skill dk-workflows:dk-pr-review --stage architecture`, with the same options and upstream; defer normal review/finalizer preflight until their gate opens. Save original instructions, settled and deferred scope, existing feedback, Decisions with sources, target, base, head and effective action policy. Direct invocation may review your PR, but never approve the authenticated account's own PR. Save the run and permissions in operational progress. Narrower new instructions revoke affected pending actions.
2. **Settle architecture first.** Follow the [architecture gate](../docs/architecture-review.md) after initial inspection and before any configured task or parallel group. Complete evidence-backed applicability, profile selection and alternatives comparison, then automatic or sourced user selection. Pending choice blocks normal reviewers. Publish only the settled Architecture decisions subsection within `permissions.edit_architecture_decisions`; analysis-only prevents publication. Check current implementation alignment. Independently verify a material mismatch inside this stage, publish its substantive required design changes as `REQUEST_CHANGES`, and stop with an explicit architecture-only completed outcome. Do not run ordinary reviewers or approval/merge finalizers on this path. Missing evidence, uncertainty, denied permissions or unavailable native verification remain privately incomplete. Derive release from accepted managed tasks and reconciled publication receipts with `architecture.py gate`; pass refs as `definition.options.architecture_evidence` to normal task occurrences. After changes, use targeted impact assessment and fresh alignment; preserve unchanged alternatives and original evidence. Disabled architecture bypasses all architecture stages and publications without deleting evidence. Once released, preflight `--stage review`; preflight finalizers only at their own boundary. Give normal reviewers the settled decision's governing evidence.
3. **Find issues.** Apply [finding follow-ups](../docs/pr/finding-followups.md) to complete discussion and retained original findings, including reports from bots, people and earlier runs. Give discovery and verification historical candidates that may remain actionable; duplicate suppression must not hide them before current-head verification. Use the deterministic follow-up inspection for source/commit anchors and existing publication operations. When discovery or verification needs a new pass, check the remaining budget and save the cycle id. Complete preceding configured tasks before capturing final discovery inputs, refreshing inspection after their effects. Follow [the reviewer recipe](pr-reviewers.md) for the selected discovery invocation, normally `dk-workflows:dk-pr-reviewers-run`. Pin complete inputs and save reports and native handles. Manage claims and reuse through [task state](../docs/task-state.md). Use the saved `run` and `cycle` in prepare requests for discovery and verification in this pass. Changed source inputs require a new cycle; unchanged reuse uses none. Keep candidate findings separate from confirmed issues. Missing or incomplete required reports block a clean verdict. Preserve completed tasks. Follow [native handoffs](../docs/native-review.md).
4. **Verify independently.** Give a fresh native agent the candidate findings, original evidence, pinned source, governing scope and complete discussion. Assign verification only, without fixes or publication. Require it to challenge each claimed failure, inspect surrounding behavior and tests, reproduce when useful, check settled or intentional behavior, and check for prior fixes or reports. Return `confirmed`, `rejected` or `uncertain` for each finding, with source or reproduction evidence and severity. For historical candidates, separately recognize completed fixes and explicit accepted/deferred dispositions. Follow the finding-specific substantive-request and age procedure in [finding follow-ups](../docs/pr/finding-followups.md); recent or unknown age affects reminders only and never clears an unresolved finding from readiness gates. Confirmed findings also need a changed-line location. Preserve disagreements. No candidates means no verification invocation, but required discovery coverage must still be complete.

   Prepare the selected verification occurrence with `prepare --file REQUEST.json`, using a descriptor with `kind:"skill"`, `skill:"dk-workflows:dk-pr-review"`, `selection:"tasks"` and flattened `index`, and a definition with responsibility `finding-verification` and the exact resolved skill identity. The bundled instruction-only verification uses this owning skill's identity. Capture this skill, recipe, all governing references, original candidate outputs, configured prompt/model/effort and exact pinned inputs. Predeclare the complete `native_review` execution contract and retain observed native root, child and driver evidence under [native handoffs](../docs/native-review.md); submit original output with `finish --native-evidence` and satisfy its checklist before accepting verification. Follow the [invocation contract](../docs/invocations.md). Assign verification only and use a fresh independent native agent; do not invoke the full workflow recursively. Use the reviewers' claim, native outcome and recording contract. Failed or incomplete verification leaves candidates unverified. Save and recover it explicitly. Record the failed or incomplete attempt before any eligible retry in the same cycle, bounded by resolved `limits.retries_per_task`. Set `retry:true` in the prepare request immediately before retrying, never on initial invocation. Uncertain findings block CI workflow approval, PR approval and merging, even if confirmed findings can be posted.

   Complete subsequent configured tasks in list order. Resume unfinished occurrences and retain unchanged completed results. Required failures block the next boundary. Refresh affected evidence after task effects; changed review inputs require another pass within the retained budget. Every task inherits this workflow's permissions, including its prohibition on fixes and branch pushes.
5. **Prepare and post.** Apply [finding follow-ups](../docs/pr/finding-followups.md) before suppressing previously reported findings. After at least two new PR commits since the latest substantive report/request, an independently confirmed actionable finding receives a targeted, source-linked fix request when posting is authorized. Reply in its original inline thread or use a source-linked response for a review body/top-level finding. Count recent equivalent requests and original publication operations; unchanged reruns, one new commit and formatting-only bot-summary edits must not cause another reminder. Exclude fixed, resolved, rejected, uncertain and explicitly accepted/deferred findings. Use the transient helper plan and existing reply journals, preserving uncertain-write reconciliation. Suppress other duplicates already covered by current discussion or your reviews, including prior runs; never publish both a follow-up and a new duplicate inline finding. Post only confirmed actionable issues with evidence and changed-line locations. Honor the selected review publisher's `blocking_event` and `nonblocking_event` for completed verified findings (defaults `REQUEST_CHANGES` and `COMMENT`). Partial reviews use `COMMENT` for independently confirmed findings only, with coverage and verification blockers reported privately. Leave the general body empty unless a substantive repository summary was requested or the selected publisher's `include_summary` option is enabled. Withhold unverified findings or unsupported replies; never substitute operational diagnostics. Never report partial or uncertain coverage as clean. Before publication, refresh head, target, scope and discussion, then recapture affected tasks. Changes require reassessment and fresh verification. Cached findings do not authorize actions. Use the configured publisher, normally `dk-workflows:dk-pr-review-post`. Save exact payloads and operation receipts. Reconcile uncertain writes read-only before retrying.
6. **Approve fork CI when ready.** When selected in the finalizer list, run `dk-workflows:dk-ci-approve` after discovery, independent verification, finding dispositions and publication reconciliation finish, subject to resolved `permissions.approve_fork_ci` (default true). The default list places it before CI and optional PR approval/merge, independently of whether PR approval or merging is enabled. Analysis-only instructions disable mutations. Follow [CI approval evidence](../docs/pr/ci-approval.md): require another author's open non-draft PR, complete current review and necessary verification, no unresolved actionable or uncertain findings, reconciled publications and unchanged reviewed head, target and governing context. Read original outputs and recapture current task coverage; `ready:true` alone is insufficient. Successful CI and human PR approvals are not prerequisites. Save each journaled run/attempt receipt or the verified no-op. Permission failures, ambiguous associations and changed inputs block this action. Retain partial completion and reconcile uncertain operations read-only without resending. This permits CI execution only.
7. **Approve when authorized.** Require all selected reviewers and needed verification to be complete, no unresolved blocking or uncertain findings, and current CI for the exact head through `dk-workflows:dk-ci`. Recheck feedback, rules and coverage. Post `APPROVE` only when authorized and the authenticated actor differs from the author. If PR approval is disabled, skip this action after the independent fork CI approval boundary. Do not post an empty review just to mark progress.
8. **Merge when authorized.** Preserve an explicit merge instruction passed through `dk-workflows:dk-pr-iter`, including a combined checkout, iteration and merge request. It supplies permission with resolved `permissions.merge_pr.enabled:false`; approval remains a separate action. Require complete clean review and verification, current CI, satisfied repository review requirements, and an open, non-draft, mergeable PR at the reviewed head and target. Refresh live inputs and task status immediately before dispatch. Use `dk-workflows:dk-pr-publish` with `kind:merge-pr`, reviewed `head`, reviewed target `base` and authorized `merge_method` (`squash` or `merge`). The publisher checks current readiness and binds the request to the reviewed head. It does not bypass protection rules. Save the operation. After an uncertain outcome, reconcile the exact merge commit and actor. Changed source or an ambiguous outcome blocks further writes. Do not retry a merge.
9. **Report and resume.** Return reviewer and verification completion, finding dispositions, publication links, fork CI approval, PR approval and merge receipts or blockers, and saved state references. Reread current governing inputs and recapture specs before claiming completion. Report each requested action separately: posting may be complete while approval or merging is blocked. Resume the same claims, run, retry budgets, CI deadlines and publication operations. Unchanged reruns must not duplicate comments, approvals or merges. Allow resolved `limits.review_cycles` review and verification cycles initially (default five), with at most `limits.retries_per_task` retries per task for the same inputs (default one). Stop with saved evidence when the allowance is exhausted. Distinguish ordinary recovery from an explicit new user review invocation or subsequent instruction to continue: follow [retained budgets](../docs/task-state.md#retained-budgets) to record at most one bounded `continue-run` grant for that stable user-request id, retaining the same run and exact authorization/source. A fresh session or automatic resume alone never extends the allowance. Continuation does not authorize posting, CI approval, PR approval or merging and does not replace current review coverage.

Give verification its prepared mandatory checklist and finish the shared [completion checks](../docs/task-state.md#completion-checks) with that same verification agent before accepting its report.
