# Review another person's PR

This workflow discovers issues, verifies them and posts a review. It does not fix the author's code, rewrite commits, split scope, edit the PR description/Decisions, resolve the author's feedback or push branches. Use `dk-pr-fix` only when explicitly asked to maintain the PR. A direct invocation authorizes posting verified findings under effective policy; analysis-only instructions disable all publication. Approval and merging each require explicit user authorization or their own enabled saved policy from `dk-config`; authority to post does not imply either.

1. **Inspect and pin.** Resolve ownership under [PR routing](pr.md), the selected roles/reviewers under [configuration](../docs/configuration.md), and complete discussion under [shared evidence](../docs/pr/supplied-evidence.md). Preserve original instructions, settled/deferred scope, existing comments/reviews, source-linked Decisions, target/base/head and effective action policy. Direct invocation may review your PR, but never approve your authenticated account's own PR. Save the run and effective authority in operational progress; narrower new instructions revoke affected pending actions.
2. **Discover.** Invoke the configured reviewer coordinator, normally `dk-pr-reviewers-run`, under [the reviewer recipe](pr-reviewers.md). Pin complete source inputs, preserve reviewer reports and native handles, and manage claims/reuse through [task state](../docs/task-state.md). Use the retained `--run RUN_ID --cycle CYCLE_ID` for all discovery and verification claims in this pass. A source-changing refresh uses a new cycle; unchanged reuse allocates none. Keep candidate findings distinct from confirmed issues. Missing or incomplete required reviewer output blocks a clean verdict; preserve completed siblings. Native execution follows [native handoffs](../docs/native-review.md).
3. **Verify independently.** Give a fresh native agent the candidate findings, original evidence, pinned source, governing scope and complete discussion. Assign only finding verification, with no publishing or fixes. Require it to challenge the claimed failure, inspect surrounding behavior and tests, reproduce where useful, check intentional/settled behavior, and check whether the issue was already addressed or reported. Return confirmed/rejected/uncertain per finding, with concrete source/reproduction evidence, severity and a changed-line location for confirmed issues. Retain disagreements instead of treating the initial review as proof. An empty candidate set needs no verification invocation; it still requires complete required discovery coverage.
   Define a managed verification task with identity `dk-workflows:dk-pr-review`, responsibility `finding-verification`, this skill/recipe and transitive governing resources, original candidate outputs and exact pinned inputs. Its assignment is verification only, not recursive workflow execution. Follow the same claim/native-outcome/record contract as reviewers. A failed or incomplete verifier leaves its candidates unverified; retain and recover it explicitly. Capture all inputs for reuse. Record any failed/incomplete attempt before its one eligible same-cycle retry; reserve `--retry` immediately before that retry, never on the initial invocation. Retain uncertainty as a blocker to approval/merging, even when other confirmed findings can be posted.
4. **Prepare and post.** Deduplicate verified findings against current source-linked discussion and your existing reviews, including prior runs. Post only confirmed actionable issues, preserving evidence and changed-line mappings. Blocking findings justify `REQUEST_CHANGES`; nonblocking findings use `COMMENT`. Partial reviews may post confirmed findings as `COMMENT`, explicitly stating remaining coverage/verification blockers. Never present partial or uncertain coverage as clean. Before publishing, refresh head, target, scope and discussion and recapture affected tasks. Drift requires reassessment and refreshed verification; a cached finding grants no authority. Use the configured review-post skill, normally `dk-pr-review-post`, and retain exact payload and operation receipts. Reconcile uncertain writes read-only before another attempt.
5. **Approve when authorized.** Require all selected reviewers and needed verification to be complete, no unresolved blocking or uncertain findings, and current exact-head CI through `dk-ci`. Recheck current feedback, rules and review/verification coverage. Post `APPROVE` only when enabled and the authenticated actor differs from the PR author. If approval is disabled, return the completed review or post confirmed findings; do not emit an empty review solely to mark progress.
6. **Merge when authorized.** Require complete clean review/verification, current CI, satisfied repository review requirements and an open, non-draft, mergeable PR at the reviewed head and target. Refresh live inputs and task status immediately before dispatch. Use `dk-pr-publish` with `kind:merge-pr`, reviewed `head`, reviewed target `base` and the authorized `merge_method` (`squash` or `merge`). The publisher verifies live readiness and binds the merge request to the reviewed head; it never bypasses protection rules. Preserve the operation and reconcile the exact merge commit/actor after uncertainty. A changed source or ambiguous outcome blocks further writes; do not retry a merge.
7. **Report and resume.** Return reviewer/verification completion, confirmed/rejected/uncertain dispositions, publication links, approval/merge receipt or exact blockers, and retained state references. Recollect live governing inputs and recapture specs before claiming completion. A posted review can be complete while approval or merging is blocked; name each requested action's outcome separately. Resume the same claims, run, retry budgets, CI deadlines and publication operations; unchanged reruns must not duplicate comments, approvals or merges. Bound source-changing refreshes to five review/verification cycles, retaining one same-input retry per task. Stop with retained evidence if the budget is exhausted.
