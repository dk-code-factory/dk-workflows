## Initial feedback work

Inspect every inline item and top-level comment or review body. Record informational messages, bot status, acknowledgements, feedback already answered elsewhere, and requests solely to squash or regroup commits as needing no reply, with evidence; do not answer every message mechanically. Do not treat a squash-only request as actionable feedback or leave it outstanding. Assess the full series independently during mandatory cleanup below. Deduplicate review-body requests that repeat inline feedback while retaining their source references. Classify each actionable claim as `valid`, `already_fixed`, `unsupported`, or `pre_existing` after checking head and base. Assess scope separately with `run_state.py assess --ref REF --head SHA --preparation-id ID --disposition within_scope|outside_scope|decision_blocked --evidence SOURCE --reason TEXT`. These assessments retain reference/head/preparation history. A valid excluded defect must not become `unsupported`. Run `fix-plan --ref REF --head SHA` before dispatching a fix and require `action: fix`; the selector consumes scope before size/validity. Fix only valid claims within the prepared scope and remediation depth; record exclusions and decision holds with exact evidence. For a valid pre-existing issue, estimate production-code additions plus deletions before editing: fix at **20 lines or fewer**; defer larger fixes in the final local report with evidence. Do not create a GitHub issue. Record reasons for every classification and deferral. Apply that size limit only after scope assessment; a small fix never authorizes excluded work. Verify reproduced behavior, coherent placement, sufficient tests, compatibility and cumulative design cost. Passing tests and a clean reviewer result do not justify excess complexity or testing.

For a material architecture, behavior, compatibility, or scope choice, write a concise problem statement and viable options with pros and cons. Have an **independent agent** check the evidence and comparison. If existing scope and settled Decisions clearly choose an option, publish that decision through [dk-pr-decisions](../../dk-pr-decisions/procedure.md) and implement it. Otherwise ask the human, record the answer through that skill, and resume dependent work only after the answer. Immediately use `add` to persist the selected PR-level choice with the exact user instruction or source evidence or `replace --id` when it supersedes an active choice, then draft and review affected scope prose through `dk-pr-description` and call Decisions `publish --description-file BODY --description-review-state TOKEN` under this skill's existing authorization. This composes prose and Decisions through one guarded edit while preserving unrelated content and title. Preserve exact user answers/rationale, publication intent and verified result. Pending/uncertain publication remains `sync_pending`; reconcile live state before retrying. Inspect `status` and `publication` for pending or failed writes; `add` and `replace` alone do not publish. Refresh verified context and preparation after recording or publishing the choice, even at unchanged head; dependent work resumes only when material choices agree in PR scope and Decisions. Continue independent fixes while waiting.

Apply [the pending user decision rule](../../dk-pr-reply-review/procedure.md#pending-user-decisions) to affected thread replies as well as implementation. This skill's reply authorization does not permit publishing a recommendation or “awaiting a decision” reply while the user's answer is pending. Carry the pending question and affected thread references into run records and agent handoffs.

When a human choice blocks dependent work, read and follow [the decision-question format](decision-question.md). Ask about concrete behavior or PR scope. Offer cycle-only deferral only for a concrete reason to wait or an explicit user request; preserve its scope and revisit condition on resume. Present a short problem statement and numbered options, each with separate **What changes**, **Pros**, and **Cons** paragraphs. Mark the recommended option and add **Why recommended** explaining why its benefits justify its costs for this PR. Do not compress these into a single sentence or omit the disadvantages of the recommendation. Keep evidence links and uncertainty visible, ask for an option number, and separate operational status from the question. Use this same format for an unanswered question in the final response and in agent handoffs.

Use [dk-pr-address-reviews](../../dk-pr-address-reviews/procedure.md) for implementation and validation, [dk-commit-message](../../dk-commit-message/procedure.md) for commits, and [dk-pr-description](../../dk-pr-description/procedure.md) for a needed title/body update. Push only to the verified PR head branch, using an exact lease for rebased history. Reply to any fixed request only after its fix is on the remote head.

Assign all reply work to **one reply agent** using [dk-pr-reply-review](../../dk-pr-reply-review/procedure.md) and its [script controller](../../dk-pr-reply-review/references/reply-controller.md). Give it both complete feedback artifacts, the run record path, published code/test evidence, and current decision holds. Retain its canonical agent ID and reuse it for later replies during review and completion; do not spawn a separate top-level reply agent. The agent runs `reply_passes.py --record RUN_RECORD.json --pr PR_URL --cwd REPO --agent REPLY_AGENT_ID next` and follows its returned action and evidence paths. The script pulls complete live unresolved/unreplied feedback and controls phase order. The same agent first matches requests from every source to inline threads and submits only the inline batch. The controller retains request/source mappings, verified reply URLs, and outstanding requests, then refreshes both complete snapshots before directing top-level work. The agent prepares a separate top-level batch containing only remaining actionable requests without a suitable inline thread, grouped by source review/comment with exact quotes and answers. Compare retained mappings with live replies, including resolved threads and equivalent answers expressed differently. New feedback needing an inline reply returns to the inline pass before top-level publication.

Each nonempty batch needs independent read-only validation and its own approval through the existing publication guard, with one correction/revalidation opportunity per batch. Submit every batch and verdict, including rejections, with the controller's `publish`; it invokes the guard and preserves immutable copies of batches, verdicts, and journals plus request mappings, verified URLs, and outstanding/held requests under `reply_workflow` in the run record. Empty passes skip publication; they submit without a verdict only if they do not restore or dismiss a still-present stale request. Stale reassessments need independent approval with the same correction limit. A final rejection stops further reply publication in this run, including completion; a changed head or uncertain publication stops for reconciliation. See [run record details](run-record.md). On resume, restore this history into the reply agent and run the controller's `reconcile` against live GitHub before drafting remaining replies. Do not bypass the controller with low-level publication commands. Do not pass top-level references to inline-thread reply or resolution mutations. Do not post a standalone summary review.


Record the invoked iteration resolution authorization for the exact PR/selection before the reply agent starts. After verifying an inline reply, have that same agent follow the controller's `resolve` action and assess each `resolution_candidates` thread against the complete conversation and published code. Resolve fully answered requests through the guarded assessment/receipt flow, then refresh with `next` before continuing the inline/top-level passes. An adequate existing reply means resolve only. Do not wait for overall review, CI, commit-series cleanup or the final completion agent, and do not ask again for already supplied resolution permission. Keep disputed, partial, unpublished, held and pending-decision work open with reasons. Complete this independent cleanup even if a provider failure blocks later PR completion; preserve all other publication, rejection and uncertainty guards.
