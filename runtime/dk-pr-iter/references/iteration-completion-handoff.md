## Completion handoff

A prepublication `cleanup_prechecks` receipt cannot supply final review coverage or authorize completion. `--cleanup-precheck` is accepted only by the review-stage gate. Report review readiness separately from cleanup and completion readiness.

After cleanup, consume the refreshed preparation and current engineering verification. With preparation v3 and review-result v3, an operational refresh that changes `preparation_id` can retain review coverage at the same head when the runtime-computed `engineering_id` is unchanged and the existing coverage gate accepts reuse. Do not request reconciliation solely because provenance IDs differ. Current evidence, retained reviewer bindings, engineering verification and exact-head CI still require validation. A changed head, including tree-equivalent regrouping, follows the guarded cleanup and reconciliation path; matching engineering IDs alone cannot authorize it.

Legacy review-result v2 retains its stricter preparation/provenance checks through its retained runtime; do not adopt a legacy active run into the fresh contract. When the coverage gate requires reconciliation, use `run-state reconcile-review --head FINAL_SHA --series-assessment ASSESSMENT.json` and require success before completion. Pass the applicable immutable reconciliation path with the original reviewed head/tree and the exact fingerprinted cleanup assessment. The gate selects and validates this evidence against the active run/cycle/attempt and original result, preserving findings, reviewer accounting and accepted-failure requirements. Historical success at another assessment path cannot replace it. Report retained coverage and zero newly executed reviewers when reconciliation supplied coverage. A substantive or ambiguous change remains a blocker, including after cycle five; matching IDs, concurrent approval or byte-identical evidence copied to another path cannot override a persisted disagreement.

For an incomplete review with explicitly recorded human acceptance, omit `--review-complete`; the gate verifies exact-result acceptance without changing review status. Continue all cleanup/completion stages when that gate is clean, reporting accepted failures. Already-authorized thread resolution belongs to initial reply cleanup and does not wait for this gate.

Run `scripts/completion.py --cwd REPO --pr PR_URL gate --start-head START_SHA --final-head FINAL_SHA --preparation-file PREPARATION.json --verification-file VERIFICATION.json --run-record RUN_RECORD.json --review-complete --series-assessment ASSESSMENT.json` (add `--actionable` when work remains). This defaults to `--stage complete` and requires the verified assessment plus unchanged published tree, head, target tip, and fresh exact-head CI. A saved `known_flakes` or `accepted_exceptions` label cannot authorize completion. Require `gate: clean`; otherwise report the blocker without spawning a completion agent.

Spawn **one separate completion agent** only after that gate passes. Give it the selected prompt verbatim, retained PLUGIN_ROOT, calling host, parent invocation path/token and DK_CLI_REFERENCE, PR identity and repository path, starting head, reviewed head/tree and target tip, verified cleanup assessment path and final published head, review cycle result, exact-head CI result and shared policy evidence paths (including ignored failures with issue links, raw result, discovery limits, and missing evidence), the full run record **path**, both refreshed feedback snapshot paths, the reply agent's canonical ID and saved reply-history paths, and the refreshed decision context, preparation artifact paths with both preparation_id and engineering_id, engineering verification artifact and summary. Carry the child lifecycle rules from the coordinator handoff: native DK skills retain their own invocation, and task-only children do not complete the parent. Completion must verify placement, test sufficiency, compatibility and cumulative design cost against preparation regardless of review convergence; custom prompts cannot bypass unresolved preparation or synchronization gates. Record this handoff including the assessment path. The completion agent consumes the verified cleanup result and must not assess or rewrite the series again. It coordinates missing replies and guarded `reply_passes.py resolve --assessment FILE` calls with the existing reply agent, waits for verified results, and preserves rejection limits and uncertain-publication stops. Record the iteration resolution authorization with the exact PR selection; reuse adequate existing replies and track unresolved cleanup separately from the controller's `done` action. A selected review link retains its scope through completion and resume. It must recheck live state and run the same **complete** gate with `--series-assessment` before acting, refreshing issue states and head/attempt provenance. For the default prompt, follow [the completion procedure](default-completion.md). An override may change the completion action within the authorization above; it cannot skip or weaken cleanup or its gate. The completion agent reports every action or blocker to the parent.

Record the terminal run outcome with `finish-run --status completed|limited --reason TEXT` after completion actions or a terminal limitation; interrupted work stays active for explicit resume. A terminal marker records an outcome, not proof of clean completion. Finish with the current head, iteration run ID, completed cycle count, published fixes and replies, CI status, cleanup outcome and assessment path, completion actions and blockers, deferred items with evidence, and verified flaky tests and related issues. Distinguish a completed review cycle from completed thread cleanup. Report every open actionable thread and outstanding actionable top-level request with its source URL and reason. Squash-only feedback is ignored editorial feedback, not an outstanding request. Do not describe completion as done if a fully answered actionable inline thread lacks a reply or resolution, or a completed actionable top-level request lacks either a source-linked quoted reply or a recorded mapping to its verified inline answer. A request already answered in its matching thread needs no duplicate PR-level comment. Top-level feedback has no resolve operation.

Report reviewers actually executed during this invocation separately from results reused from earlier work. If no runner executed, say zero reviewers executed and identify any prior coverage used. Include reviewed commits and trees, skipped reviewers and reasons, current final-tree coverage, and any cap or provenance limitation. Fresh CI alone must never be described as fresh code review.
