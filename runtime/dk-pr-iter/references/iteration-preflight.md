## Preflight

Read and follow [metadata readiness](metadata.md) first. Complete the tool, configuration, rule, thread, and decision-context checks below before any branch or GitHub mutation. A cold cache requires initialization; it is not proof of missing decisions or a clean review.

1. Identify the PR's base repository and its head repository, branch, and SHA. Use the PR URL for GitHub queries and CI waits so a checkout of a fork cannot select another PR by branch name. Run `$dk-config --pr PR_URL refresh`, read applicable repository rules and `AGENTS.md`. Read the linked issue, PR scope, and live `## Decisions` section. Check the worktree and push access to the head repository, including forks.
2. Fetch the **complete** unresolved-thread snapshot using [dk-pr-address-reviews](../../dk-pr-address-reviews/procedure.md)'s deterministic fetcher. Require successful exit and `complete: true`. Use its PR title, description, head repository and branch, base and head SHAs, and closing issue references as the saved context; avoid redundant `gh pr view` reads of unchanged fields. Always fetch top-level reviews and general PR comments with that skill's `fetch_pr_conversation.py --snapshot-file SNAPSHOT_FILE --cwd REPO`, even when the unresolved inline list is empty. Require successful exit, `complete: true`, and the same PR URL and head. Use the inline snapshot's `items` plus the conversation artifact's `items` as the feedback worklist. Account for each `reference` using the full conversation, current PR head, and base. Read all later top-level comments before deciding whether an earlier request needs a reply; these comments have no resolved flag. Recheck head SHA before each mutation; an external head change stops the current agent or CI wait and requires fresh preflight and classification.
3. Create or inspect the per-PR record outside the repository using `scripts/run_state.py`. For a new request after a terminal run, use `start-run`; this archives the prior run and starts a distinct run with a fresh five-cycle budget. Use `resume-run` only for interrupted active work, preserving its counters. Never treat a completed run as a resume. An active run blocks `start-run`; reconcile and record its actual terminal outcome before a later user request can start another. For a legacy record, use `adopt-run` to preserve its counters, then explicitly record the known outcome; never silently reset an exhausted budget. Do not finish and restart within one request to evade a cap. Preserve publication events, reply-controller history, local decisions, and per-head rerun limits across runs. Record thread classifications, evidence URLs, decisions with sources (`decision --text TEXT --source SOURCE`), deferred items, pushes, replies, CI attempts, and cycle counts. Keep this record as operational history. Immediately persist agreed PR-level choices through Decisions `add` or explicit `replace`, preserving the exact user instruction or source evidence; a run-record entry alone does not persist a choice in Decisions. Restore `local_decisions` from this record on resume as temporary context, reconciling them against active persistent Decisions so superseded choices cannot reactivate. Export `dk-pr-decisions/scripts/decisions.py --pr PR_URL context --local-decisions-file RUN_RECORD.json` to a JSON file outside the repository. Require `schema_version: 2`, `status: ok`, and `data.verified: true`. Read active entries in `data.decisions`; superseded entries are history. Pass its path and a concise decision summary to every code fixing, review cycle, and CI repair agent. Include the preparation path/ID once assembled in step 4. Refresh it after a new decision, PR body edit, or head change. Missing, unreadable, malformed, stale, or conflicting context blocks dependent work until reconciled. Before any publication, reconcile the record with live GitHub state so an interrupted run cannot duplicate a push, decision, reply, or rerun.
4. Before handling local changes, rebasing, initial fixes or review, follow [engineering preparation](../../dk-pr-decisions/references/preparation.md). Pin an isolated remote checkout with `dk-pr-review/scripts/review_context.py`, discover configured effective reviewer descriptors, and assemble the complete original-evidence manifest including exact user instructions, local choices, questions and prior preparation. Run Decisions `prepare` in `iteration` mode. Require `ready`; register it with `run_state.py --repo HOST/OWNER/REPO --pr NUMBER preparation --file PREPARATION.json --pr-url PR_URL --head SHA`. Before dependent mutations and initial/CI fix handoffs run `work-gate --head SHA` and recheck live PR scope/head. Refresh after code, scope, answer or instruction changes without resetting counters or assessments. Retain immutable snapshots for `run_history` evidence so routine operational events do not invalidate their own preparation; work gates separately detect changed local decisions. A material proposal or pending synchronization blocks affected work even after clean reviews.
5. Before rebasing, inspect staged, unstaged, and untracked changes (`git status --porcelain=v1 --untracked-files=all`); read their contents and compare each change with the PR scope, current head, settled Decisions, and any review request it may address. Validate in-scope changes, stage only relevant files or hunks, and commit cohesive work to the PR branch using `dk-commit-message`; include those commits in the rebase, review, and publication flow. Discard only changes proven to contain no unique work, such as generated artifacts or edits already present on the PR head, and only after preserving a recoverable copy outside the repository; inspect and remove staged and untracked content explicitly rather than using a blanket clean or reset. Preserve unrelated work and continue from a clean linked worktree at the verified PR head when possible. If ownership, scope, or whether a change is safe to discard remains uncertain, stop and ask the human before touching it. Report how every initial change was handled. Stop on an unsafe or ambiguous branch, incomplete evidence, or missing reviewers. Fetch the target branch from the base repository, verify its remote tip and the PR head against the head repository again, and rebase the PR commits onto that tip before classifying or reviewing. Resolve conflicts against the PR's intended scope and validate the result. Publish the rewritten branch only to the verified head repository with `git push --force-with-lease=<head-ref>:<previous-remote-head>` after rechecking both remote refs; a lease failure or external head change requires fresh preflight. Recheck the base target tip before each review cycle and before publishing a code change; if it advanced, rebase again, validate, and restart the affected review or CI observation against the new head. Never rewrite unrelated commits or use a plain `--force` push. Refresh the thread snapshot, decision context and preparation against the resulting head before classifying or reviewing.

Keep large evidence outside the conversation: save complete thread snapshots, complete top-level conversation, CI responses, and broad diffs to files outside the repository, then print a concise index or summary. Give agents the artifact paths and relevant thread references so they can read the same pinned evidence. Read the specific conversations, changed files, and error excerpts needed for each decision. Preserve the full artifacts and inspect them when completeness or a disputed claim requires it; do not truncate evidence used to classify a thread or verify a failure.

Spawn agents for this workflow with `fork_turns="none"`. Give each a short, self-contained handoff: its task and permitted actions, PR URL and repository path, pinned head and any relevant base, applicable user constraints, required skill or procedure, artifact paths, and the specific references or failure excerpts it needs. The agent reads full evidence from those files when needed. Do not paste the parent conversation, broad diffs, thread snapshots, or run record into the handoff. Include the governing preparation path/ID, selected remedy, principal production/test locations, reusable helpers/fixtures, behavior and test scenarios, commands and stopping criteria. Workers record routine adjustments with rationale and return material ownership, interaction, design or validation changes to the coordinator before dependent work. Include the selected completion prompt verbatim when handing off completion. Include the waiting and message policy below in every self-contained handoff, including when delegating this entire workflow; it applies to the caller, workflow agent, and nested workers.

For an interrupted invocation entering a repaired runtime, follow [the retained-run recovery procedure](run-record.md#recovery-into-the-repaired-runtime) before resuming; preserve original reviewer packages, counters and cleanup recovery evidence.
