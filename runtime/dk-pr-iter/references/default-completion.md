# Default completion action

Act only on the identified PR and the authorized actions below. Recheck live GitHub and Git state before every remote mutation. Treat the supplied run record as operational memory, not proof of a remote result. Validate the active iteration run and its mandatory configured-reviewer result artifact against the final tree, scope and Decisions; `--review-complete` alone is insufficient. Report executed and reused reviewers, reviewed heads/trees and skipped reviewers with reasons. A final-cycle fix without coverage is a limitation, even with green CI. If the review is incomplete, actionable in-scope work remains, CI is neither successful nor freshly verified red-CI acceptance (`known_flakes` or `accepted_exceptions`) on the current head, or the PR head changed outside this run, report the status and perform no completion actions. Validate the parent's current ready preparation and engineering verification artifact and verify behavior, placement, test sufficiency, compatibility and cumulative complexity, even if review converged immediately. Unresolved scope/design/validation questions, stale sources or pending synchronization block completion and cannot be bypassed by custom prompts. Consume the parent's verified commit-series cleanup artifact; missing, stale, or incomplete cleanup blocks completion. Custom prompts cannot bypass this requirement. Before acting, run `scripts/completion.py --cwd REPO --pr PR_URL gate --start-head START_SHA --final-head FINAL_SHA --preparation-file PREPARATION.json --verification-file VERIFICATION.json --run-record RUN_RECORD.json --review-complete --series-assessment ASSESSMENT.json` and require `gate: clean`; add `--actionable` when work remains. For red CI this refreshes linked issues, checks every failed test/step, and rechecks exact head and run attempts through the shared policy. Saved red-acceptance JSON alone is insufficient; reload current CI exceptions and linked issues through the shared policy. Repeat the live gate before subsequent mutations when CI or issue state may have changed. Never merge the PR. Carry the parent workflow's waiting and message policy into any agent handoff: block on agent notifications within runtime limits, do not query status on every timeout, and report only actionable changes or completion. Do not relay unchanged worker or CI status back through each coordinator.

1. Check the PR title and description against the final published diff, linked issue, template, and settled Decisions. If either is stale, draft and review through `dk-pr-description`. If scope and Decisions both change, compose and publish the reviewed body through the Decisions publisher in one guarded edit, then refresh verified context and preparation. Preserve unrelated prose and title. Record whether an edit was needed and verify the published fields. The full series was assessed and any needed cleanup published before this handoff. Consume that verified result; do not assess, squash, split, or otherwise rewrite the series again. A request solely to squash or regroup commits is editorial feedback: record it as ignored without a reply, resolution, or blocker. If that request also identifies a code or description defect, handle the defect separately.
2. Audit **every** inline review thread using `python3 scripts/completion_threads.py --cwd REPO --pr PR`. Require `complete: true`, the expected head, and `threadCount` matching the `threads` list. This command uses the shared fetcher's complete thread and comment pagination, including resolved threads, and requires two matching snapshots. When given a review link, preserve the anchor and limit the audit worklist and mutations to its `selection.threadReferences`, while retaining all threads for context. For each selected open thread, read the entire conversation and the published code; classify every request as fully answered, still open with a specific reason, or squash-only editorial feedback. A fully answered request on the published head must have a verified adequate reply in its own thread and be resolved. A supported existing explanation qualifies; retain its URL and normalized `text`, without requiring it to match a newly proposed acknowledgement. Coordinate missing replies with the run's **existing reply agent**, using its canonical ID and the same run record. Have it follow `dk-pr-reply-review`'s [script controller](../../dk-pr-reply-review/references/reply-controller.md): `next` pulls both complete live snapshots and directs inline matching from all sources before any top-level publication. Do not spawn another reply agent or draft replies in the completion agent. Wait for verified inline results and retain their mappings/journals. Record the existing iteration resolution authorization in the run record as described by the controller. Have the same reply agent submit `reply_passes.py resolve --assessment FILE` for each fully answered thread, pinning the head, scope, conversation, verified reply, and supporting evidence. Reuse an adequate reply and resolve only; otherwise wait for verified publication before assessing resolution. Preserve resolution intents/receipts and use `reconcile` after uncertain outcomes; do not issue direct resolution mutations. An earlier promise to fix does not count as a completion reply. Already resolved threads are complete. Leave disputed, deferred, partially answered, and pending-decision threads open and report each reason. Leave squash-only threads alone and do not count them as incomplete cleanup. After all actions, fetch another complete snapshot and reconcile every thread: if a fully answered thread remains unanswered or unresolved, thread cleanup is incomplete and completion must report that blocker, not success.
3. Audit top-level feedback as well, even when there are no inline threads. Reuse the **same reply agent** and controller state for this second pass. Its `next` must refresh both complete feedback snapshots after inline publication and any resolution, including resolved threads and later comments, before it prepares a top-level batch. Reconcile each actionable request against published code, retained source mappings, and live replies; skip informational feedback, squash-only requests, and equivalent answers expressed differently, retaining verified answer URLs. Only remaining actionable requests without a suitable inline thread receive a source-linked response, grouped by source review/comment with exact quotes and answers. If new feedback needs another inline reply, follow the controller back through the inline pass, resolve eligible fully answered threads, and refresh both snapshots again before top-level publication. Each nonempty batch needs its own independent validator approval and one correction opportunity; a final rejection or uncertain publication stops further replies, including completion. Empty phases submit their mappings without validation/publication. Preserve pending-user-decision holds. Do not resolve top-level feedback or post a general summary. Call `next` after publication to refresh and verify cleanup; its `done` action still requires inspecting `unresolved_threads`, `cleanup_complete`, and outstanding holds. An open squash-only thread may remain a documented editorial exclusion under step 2; report that exception explicitly instead of treating `done` as cleanup proof. Report each outstanding actionable request by source URL and reason; missing responses to completed requests make feedback cleanup incomplete.
4. Only after the final published head has successful CI or freshly verified red-CI acceptance (`known_flakes` or `accepted_exceptions`) and both inline and top-level feedback cleanup are complete, re-request reviews from eligible human and bot authors of submitted reviews. Paginate all submitted reviews and pending review requests. Exclude the PR author, anyone with a submitted review on the final head, anyone already pending, and anyone already requested by this run for that final head. Use GitHub's REST `POST /repos/{owner}/{repo}/pulls/{pull_number}/requested_reviewers` with the user's login. Check the head and pending requests immediately before each call, record each attempt and confirmed request by final head, and report users GitHub rejects. An uncertain response requires live reconciliation before retrying; never send duplicate notifications.

Report the final head, cleanup outcome and assessment path, title/body check or edit, CI evidence (for `known_flakes`, say “CI red; accepted known flakes” with issue links and raw `failure`; for `accepted_exceptions`, say “CI red; accepted configured exceptions” with setting IDs, scopes, reasons and raw `failure`), discovery limits and missing evidence, replied and resolved threads, source-linked top-level replies, every outstanding actionable feedback item with its reason, review requests, and any blocked or rejected action. Stop on a changed head, incomplete pagination, or uncertain mutation instead of guessing.
