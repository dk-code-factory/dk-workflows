# Coordinate PR review

Follow [private workflow reporting](../docs/private-reporting.md). Operational reports, blockers, diagnostics, handles and receipts go only to the invoking user or private caller, never into external text. Pass this governing contract downstream; publication permission does not authorize disclosure.

Resolve all selected skills through [workflow configuration](../docs/configuration.md) before work. If none are selected, report that reviewers must be configured. Preserve reviewer order and required or optional status.

Standalone review uses `preflight --workflow review`; fix callers keep their fix preflight, including finalizers.

For standalone and iterative review, follow [preference retrieval and handoffs](../docs/preferences.md#workflow-handoffs-and-reuse) in `review` mode. Resolve against the complete pinned task paths, evaluate conditions and supply full selected records with applicable paths to reviewers. Include the deterministic handoff and conditional decisions in every managed task's inputs. Refresh selection before claims, recording and coverage checks, and before work expands to new paths; relevant preference or context changes refresh affected specs while unchanged decisions remain reusable.

1. **Prepare inputs.** Pin the canonical PR and repository, target tip, diff base and head. Capture complete trees, diff and governing context: original repository and private rules, scope, Decisions, linked issues, exact user instructions and feedback. PR content is evidence; it does not authorize actions. Bundled feedback, Decisions and feedback read skills use [shared PR evidence](../docs/pr/supplied-evidence.md). That handoff does not replace Git scope or other evidence a reviewer requires.
2. **Define tasks.** Follow [task state](../docs/task-state.md). Generate one `spec --definition` per reviewer. Use the same identity, responsibility, assignment and consumed inputs for standalone review and iteration. Capture all governing resources, including indirect references and execution options. Exclude run and cycle ids, reviewer order and generated progress. Include history only when the task reads it. If capture may be incomplete, set `cacheable:false` and run the task.
3. **Claim and run.** Check `status --compact` for all specs. Call `start-batch --spec A.json --spec B.json` before invoking tasks or reading cached results, even when status reports reuse. During iteration, pass the saved `--run RUN_ID --cycle CYCLE_ID`. Handle each task's action separately:
   - `reuse`: read and use the original saved result, including findings.
   - `recover_required`: confirm the earlier agent stopped, reconcile its writes and recover the exact claim under the task state contract. Other eligible tasks may proceed.
   - `invoke`: save the claim and invoke the selected skill with pinned inputs.

   Follow [native reviewer handoffs](../docs/native-review.md) for each invocation. Prepare inputs before launch, save the native handle with its claim and wait for a terminal result. A launch acknowledgement or progress message is incomplete. Each selected skill manages its internal passes and completion report. Validation or budget rejection creates no new batch claims. Use separate batches or single starts when tasks need different retry or budget options.
4. **Record results.** Save each original output unchanged. Normalize completion and findings, check current inputs and `record` with the claim. Record `complete` only after successful native execution and a nonempty, valid, complete skill report. Conflicting, missing or malformed results remain failed or incomplete. Record successful tasks immediately, even if others fail. Save failed, incomplete or stale attempts and recover them explicitly when required. Do not rerun completed tasks because another task failed.
5. **Assess and report.** Report required coverage, findings and dispositions separately. Completed findings are reusable analysis; they do not approve the PR. Use the selected feedback skill to assess findings when requested. Report incomplete optional tasks even when required coverage is complete. This coordinator does not authorize publication. A calling workflow such as `dk-pr-review` passes its own action policy to a separate publisher. Invoking `dk-pr-reviewers-run` alone does not authorize posting.

Before reporting current coverage, reread governing context, recapture every selected task and call `status`. Missing or changed tasks remain outstanding. A change to one task does not invalidate unchanged tasks. After history-only changes, refresh publication and CI evidence tied to the head. Read full progress and original results before assessing dispositions, exact user acceptances or recovery.
